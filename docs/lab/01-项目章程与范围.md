# 01｜项目章程、边界与预期交付

## 目标与价值

用三类**故意不同**的业务风险验证 AI 浏览器探索工具的实际效用，最终输出可以教学、复现与对照的 QA 实验工作台：

- E1（金额/交易）：通过业务规则与订单账本识别页面和服务端状态不一致。
- M1（状态机/授权）：验证升级/降级、权益生命周期、旧 Token、新旧会话与事件一致性。
- S1（时钟/并发/库存）：区分视觉现象、订单状态、独立业务账与受控并发。

成果包括：可重置 Demo、测试契约、Playwright 测试资产、可审计证据、受限 B/C 可选 PoC、实验评价报告以及 Markdown 教学文章。

## 非目标

- 不在生产环境自主发现漏洞或执行业务写操作。
- 不把某个 Browser Agent 当作可信缺陷裁判。
- 不实现完整电商平台、真实支付渠道、营销系统或高并发商业架构。
- 不承诺 B/C 一定优于 A，也不承诺 AI 一定能找到预埋缺陷。
- 不从外部仓库直接复制不兼容许可的代码或无条件启用遥测。

## 设计原则

1. **Local-first**：Demo、合成数据、测试与证据默认本地，SQLite 可用于轻量运行状态，但不要将其变成必须联网才能使用的服务。
2. **TDD**：先不变量与失败用例，再最小可运行功能。
3. **Independent Oracle**：价格、等级授权、库存/订单事实由独立后端查询证明。
4. **Human-in-the-loop**：确认缺陷、变更业务规则、准许高副作用动作必须人工审批。
5. **Evidence First**：Run ID、测试环境、版本、数据种子、动作、截图、Trace、Oracle、验证者可追溯。
6. **Three Tracks, Shared Benchmark**：A/B/C 使用相同 Fixture 与评估规则，对比应分层而非一个总分。

## 产品与参与者

| 角色 | 责任 |
|---|---|
| QA | Charter、业务预期、候选缺陷复核、Go/No-Go |
| 开发 / Codex | 搭建 Demo、实现用例与工具 Adapter，提交证据 |
| 安全/平台 | 授权范围、动作审批、隔离/网络/密钥/证据保留 |
| Eval 审核者 | 维护植入缺陷真值，不向待评估 Agent 泄露 |

## 交付定义

第一期完成 P0–P3 的确定性基线，随后在同一系统上评估 B/C。未开始或未完成阶段如实标记；不为了产生排行榜而跳过安全或独立验证。
