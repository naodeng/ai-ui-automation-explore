# 系列定位与编辑规范

## 不是六篇“工具合集”，而是每个工具自成体系
之前的六个专题保留为**每篇工具文章的可选六个知识模块**：浏览器入门、AI 辅助自动化、探索/测试设计、工程化、智能维护、选型边界。

每篇在 2026 年工具现状下，必须回答：
1. 这是哪个层次的技术（Runner、CLI、MCP、SDK、Agent、诊断、云基础设施、Benchmark）？
2. 新手如何按版本复现安装和第一个浏览器动作？
3. 能否形成可重复执行、可断言、可入 CI 的 UI 回归？不能的情况下，应该与什么组合？
4. E1/M1/S1 哪个最能展示它的优势？哪些结果需要 API / 业务账本 / 人工 Oracle？
5. 它在安全、稳定性、成本、可维护性方面的实际限制是什么？

## 文章深度的控制
- **完整篇（约 3500–6000 字，需按实测增减）**：环境 + 安装排错 + 入门 + 主案例完整 E2E + 进阶 + CI + FAQ + 比较。
- **专题篇（约 1800–3200 字）**：安装/接入 + 1 个典型任务 + 与主框架配合 + 边界 + FAQ。
- **短篇（约 900–1800 字）**：定位、如何试用、单个辅助案例、何时有用/无用、FAQ。

字数只是编辑预算，不等于质量标准；工具本身不支持时，宁缺勿编。

## 写作统一要求
- 新手版开头（为什么要用）+ QA 版主体（怎么验证）+ 进阶版结尾（工程化和治理）。
- 图：建议 1 张流程图/对比表；截图需实测生成并脱敏，不能拿营销图冒充实践。
- 代码：对当前锁定的版本运行通过后才标记为可复制；未经运行标示「示例，待验证」。
- FAQ 至少 3 个，围绕本工具独有的真实问题，不套通用问答。
- 失败记录：失败命令、报错、原因、恢复和最终证据，文章不得只展示理想路径。
- 发布 Markdown 为单一正式稿；网站和公众号复用内容时只处理平台格式，不维护矛盾版本。
