# 20｜从零开始到真实复盘：操作顺序速查

这是一份**操作手册**，不是已经执行过的结果。命令是否存在取决于 Codex 完成 P2/P3 后的项目实现。

## Round 0：解包与校验

1. 将 ZIP 解压到新的 Git 工作区，确认 `legacy-v1.0/` 原版未修改。
2. 执行 `python3 scripts/validate_kit.py`，读取输出：成功只表明静态包正确。
3. 将 `prompts/00-总控-交给Codex.md` 粘贴给 Codex；执行到 P0 结束，只让它产生 readiness。

## Round 1：冻结契约

1. P0 人工审批后用 `prompts/02-P1-契约与TDD.md`。
2. 对照三个 YAML Contract 逐个确认金额、会员授权和库存等演示假设。
3. 运行正/反例 Schema 测试；确认 Confirmed 缺人工审批时会被拒绝。
4. Review Rule ID、Oracle、Fixture、权限来源与未知规则。

## Round 2：依次构建 E1、M1、S1

1. E1：用 100/99 和同幂等键测试服务端报价与沙盒订单。
2. M1：用银→金→银和旧会话“新 Gold-only”授权建立状态机与事件版本测试。
3. S1：构建 Fake Clock、库存 100、限购 1、预占/已售/释放的真实账本。
4. 每个业务案例均要求两次 Reset 的业务状态校验一致，不得同时修改三个案例而无法追溯原因。

## Round 3：路线 A 基线

1. 运行最小 Playwright Test 基线（建议 `npm run test:e2e`，具体由 Codex 实现）。
2. 收集真实 Trace、请求 ID、只读 Oracle、Run Manifest 和 pytest/Vitest/Playwright 结果（只写实际采用的工具）。
3. 在独立控制平面打开一个故意植入的缺陷，确认测试 RED；关闭后确认 GREEN。
4. 人工复核一个候选异常，测试“观察 → 复现 → 独立验证 → 确认/否决”的闭环。

## Round 4：路线 B 可选

选择每案例一处*真正需要视觉理解*的点：E1 窄屏金额区域、M1 权益卡、S1 倒计时与排队提示。先提交数据流和费用审批，再允许使用外部模型。记录 B 相对 A 的新增发现与误报，而非只看漂亮截图。

## Round 5：路线 C 可选

先跑安全负向实验（非法 Origin、页面 Prompt Injection、预算耗尽、未知写操作），确保全部被程序级门禁阻断。通过后只执行有界的只读 Mission，不能自行发起高并发、真实订单、会员修改。

## Round 6：公平对照

读取 `templates/experiment-plan.csv` 的 36 个**计划** Run。每个 Run 重新 seed，记录实际 Run ID、时钟、工具版本、候选问题、人工确认、失败和费用。资源不足可以缩减为 Pilot，但不得写成已完成 36 次。

## Round 7：回归资产与内容

- 把人类已确认的缺陷转成稳定 Playwright/API Test。
- 确认 Bug 复现、Trace 和 Oracle 证据完整。
- 进行 Go/Conditional Go/No-Go 评审。
- 更新 Canonical Markdown，不虚构项目效果；将失败案例与误报写入复盘。

## 每轮只问五件事

1. 本轮要证明哪一项不变量？
2. 测试数据如何准备和重置？
3. 哪个只读 Oracle 能证明结果？
4. 什么会导致停止/人工批准？
5. 实际证据保存在哪个 Run ID？
