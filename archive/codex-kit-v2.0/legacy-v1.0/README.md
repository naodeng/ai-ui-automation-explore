## 内容边界与状态

1. 本包中的示例电商系统、会员规则、秒杀机制均为**教学假设**，不是具体产品已知事实。正式测试前须替换为真实 PRD、API 契约和状态机。
2. 方案中只有明确标记为**官方命令**的命令来源于已核实文档；角色分工、评分标准、架构、断言和模板是本文的 QA 工程建议。
3. **没有在真实业务项目中执行浏览器测试、压测、复现漏洞或验证这三种方案的实际成功率。** 无基准实验数据、无真实缺陷发现结论。
4. 秒杀并发正确性、超卖与幂等性不能只靠浏览器 Agent 判断，必须结合 API / k6 / 独立后端状态证据。
5. 禁止在未授权生产环境进行有副作用的自主探索；尤其禁止真实支付、秒杀流量冲击、改会员权益、删除数据。
6. 文档并不为各种工具赋予它们原生没有的功能：独立确认、测试数据重置、后台核对、门禁及审计需要由宿主系统或团队实现。

## 核心选择

- **最小落地**：A 先行。统一使用 Playwright 做执行和断言，以 CLI/MCP 接受 AI 指导。
- **UI 复杂时**：在 A 基础上增配 B；视觉模型负责发现异常线索，不单独充当业务裁判。
- **需要评估自主探索**：以 C 进行受限 PoC；执行器、证据模型、后端验证器保持可替换。
- **三个共用业务案例**：E1（优惠券与下单）、M1（会员升降级）、S1（商品秒杀）。

## 使用建议

先将 `05-三案例测试设计矩阵.md` 中的演示规则替换成项目真实规则，并建立数据准备/重置脚本；再使用 `07-可复用Prompt与探索任务.md`，选一条技术路线执行 PoC。最后采用 `06-三路线对照实验与TDD验收.md` 做同条件对比。

**发布与复用**：所有 Markdown 内保留官方资料 URL，可根据实际网站 Frontmatter 添加 title、date、tags、description；如作为系列文章发布，可将三条路线分别作为进阶篇。
