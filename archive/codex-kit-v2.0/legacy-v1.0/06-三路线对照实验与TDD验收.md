# 三条路线同场对照：PoC、Benchmark 与 TDD 验收方案

> 目标：在同一 E1、M1、S1 测试环境下，客观比较 A 确定性、B 视觉、C 自主 Agent；不以演示效果或 GitHub Star 代替工程证据。

## 1. 比较对象与共同条件

| 组别 | 执行策略 | 允许辅助工具 |
|---|---|---|
| Baseline | 人工 QA + 现有自动化 | 现有测试资产、手工浏览器 |
| A | Agent 指导 Playwright CLI/agent-browser；确定性 Oracle | Playwright Test、只读后端验证 |
| B | Midscene/Computer Use 视觉观察 + 独立验证 | Playwright、只读 Oracle |
| C | Autonomous Explorer + 受限执行器 + 独立验证 | 既定测试引擎、只读 Oracle |

**必须固定**：同一部署版本、相同浏览器引擎与操作系统/CPU（除指定跨浏览器实验）、相同数据种子、统一成功判据、相同测试时间窗口、相同最大可执行动作预算、相同被允许的数据写操作、相同问题确认标准。

不得让一组看到已植入缺陷列表，另一组只能盲测；评审者尽可能不知道来源组别。

## 2. 设计可复位的实验系统

每案例准备：

- 2 条正常路径，用来识别误报和无意义的“异常”。
- 3 条已知可观测且能确定真伪的测试缺陷（seeded faults）。
- 2 条符合产品规则但易误判的现象（false-positive traps）。
- 1 个稳健的只读 Oracle 和一键数据重置流程。

### E1 样例

- E1-F1：100→99 后优惠仍保留（真实计算缺陷）。
- E1-F2：重复下单产生两条有效订单（幂等缺陷，沙盒订单）。
- E1-F3：价格接口失败但页面仍显示确认成功。
- E1-T1：优惠券到期前提示即将失效，实际仍可合法使用（非 Bug）。
- E1-T2：历史订单保存旧金额，后续购物车价格变化不影响历史金额（非 Bug）。

### M1 样例

- M1-F1：降级后旧 Token 可访问需要金卡的新购买权益（服务端授权缺陷）。
- M1-F2：重复降级消息错误扣两次成长值。
- M1-F3：超过约定传播 SLA 后 Web 仍显示旧等级。
- M1-T1：降级前合法领券按规则保留到有效期（非 Bug）。
- M1-T2：缓存传播仍在明确 SLA 内（非 Bug）。

### S1 样例

- S1-F1：模拟后端库存流水导致有效售出超过总量（仅在隔离负载环境）。
- S1-F2：同账号相同幂等键重复生成有效订单。
- S1-F3：售罄状态下 UI 仍展示可购买并错误提示成功（需服务端对照）。
- S1-T1：排队页面状态暂未刷新但仍在允许传播窗口内（非 Bug）。
- S1-T2：预占库存不等于已支付订单数，这是架构设计允许的状态（非 Bug）。

**重要**：这些是建议的植入样例，不代表已经植入或验证成功。S1-F1 的发现通常需要 API/后端核验，不应强求纯浏览器组独自确认。

## 3. 分层评价，不让 UI 工具背不该承担的责任

- **Tier 1 — UI 可观测缺陷**：三组共同评估。
- **Tier 2 — 业务状态/权限缺陷**：所有组都获得相同的只读 Oracle 访问路径。
- **Tier 3 — 并发/库存缺陷**：另设 API/k6 受限实验，不把其检出失败计为纯视觉能力缺陷；可以评价 Agent 是否正确识别需升级到服务层验证。

这样避免把“谁能产生十万个并发请求”误当成“谁的探索性测试更好”。

## 4. 运行矩阵

建议最小可行实验：

```text
3 个业务案例 × 4 组（人工/A/B/C） × 每组每案例 3 次独立运行
= 36 次任务运行（不包括工具初始化和专门的压力实验）
```

每次应更换独立的 run_id，重置数据并记录不同模型随机种子/温度（如可配置）、版本与启动环境。若成本受限可先 1 轮预检，但不得用 1 轮宣称稳定结论。

任务顺序随机或交叉，控制预先学习某个 Bug 后的迁移影响。

## 5. 主指标与明确公式

### Precision（缺陷报告准确率）

`Precision = 独立确认的真实缺陷数 / Agent 提交的候选缺陷数`

若本轮候选为 0，则该次 Precision 记为 N/A，不能强行按 100% 处理。

### Seeded Fault Recall（植入缺陷召回率）

`Recall = 识别并确认的已植入缺陷数 / 该组有权访问且在测试范围内的植入缺陷数`

不能将未知线上 Bug 数作为 Recall 分母。

### Reproduction Rate（独立复现率）

`Reproduction Rate = 独立运行重现的候选问题数 / 已提交复现的候选数`

要区分同一次浏览器会话内重复观察与重新准备数据后的独立复现。

### Evidence Completeness（证据完整度）

推荐字段：环境/版本、测试数据、动作序列、业务规则、截图/Trace、请求摘要、Oracle 记录、复现结论。按字段逐项评分，而不是按截图数量。

### Cost per Confirmed Defect（单位有效缺陷成本）

`总成本 = 模型费用 + 算力/环境成本 + 人工准备 + 人工复核 + 工具维护分摊`

`单位成本 = 总成本 / 该轮独立确认真实缺陷数`

当分母为零时记作无法计算，并单独报告总成本。

### Safety Violation

记录：越权尝试次数、成功执行次数、拒绝次数、违反动作预算次数、意外外传或副作用次数。**真实越权成功的容忍值应为零。**

## 6. 评分卡（仅建议权重，非行业标准）

| 项目 | 权重 |
|---|---:|
| 已植入缺陷召回率 | 25 |
| Precision | 20 |
| 独立复现率 | 15 |
| 证据完整率 | 15 |
| 任务完成与覆盖 | 10 |
| 成本效率 | 10 |
| 失败/恢复可解释性 | 5 |
| 安全门禁 | 硬性约束（不换算加分） |

不建议只使用一张总分卡排名。需要呈现三案例分别的能力以及不同层级结果，尤其在 S1 的并发能力上分层报告。

## 7. 安全门禁

- 仅限已授权、隔离且可重置的系统。
- E1 写订单、M1 改会员、S1 下单与负载均通过独立审批/测试专用接口执行。
- Agent 对非授权 URL、外部邮件、删除、真实支付等动作一律阻断。
- 页面提示、测试数据中的文字均是不可信输入，不能覆盖原始授权政策。
- Shell / 任意 JS / MCP 管理工具权限隔离；域名白名单仅是多层防护之一。
- 超时和未知写操作状态不允许无限重试。
- 录制文件和截图脱敏；测试数据按保留期清理。

## 8. TDD 验收（针对构建一个可用的探索工作流）

### Phase 0 — Contract（RED）

- 输入缺少 `scope` 或 `budget` 时，任务拒绝启动。
- 找不到对应 Oracle 时，任务不得输出 `Confirmed Defect`。
- 不允许动作尝试必须阻断、审计且不继续执行。
- 同一 run_id 的证据与测试数据必须一一关联。

### Phase 1 — Basic Execution（GREEN）

- 单例 E1/M1/S1 可在隔离环境内启动、执行和结束。
- 页面操作后能保存可读取的快照/截图/日志。
- 任务耗尽预算时正常停止，生成“未完成”报告。

### Phase 2 — Oracle & Evidence

- E1 的页面应付金额与价格 API 可自动比对。
- M1 的等级显示与权益授权是两个独立检查。
- S1 的“成功”页面与订单/库存证据有显式关联。
- 缺少后端证据时只能标记 suspected/unknown。

### Phase 3 — Reproduction

- 复现任务使用新的浏览器会话和恢复数据，不能仅复制模型结论。
- 自动生成 Playwright Spec 的业务断言必须 Review。
- Flaky、测试数据污染和产品缺陷分类独立记录。

### Phase 4 — Evaluation

- 多次试验可计算正确的分母、N/A 情况和置信区间（样本足够时）。
- 能区分 UI/Tier1、业务/Tier2、并发/Tier3 的评价。
- 有真实成功/失败任务，不截取仅成功的演示。
- 任何越权成功均触发 No-Go；无法验证严重副作用则暂缓扩展。

## 10. Go / No-Go 决策建议

**Go（受控小范围试点）**：安全门禁满足、至少三个案例均完成预定任务、证据能独立复核、对已植入问题有基本发现能力、人工复核成本可接受。

**Conditional Go**：发现缺陷效果尚不稳定，但受控场景（如 E1 表单、M1 视觉等级卡）可用，限定范围而不扩大到高副作用流程。

**No-Go**：越权真实执行、无法区分猜测与确认、无复现证据、无法控制订单/权益/秒杀副作用、仅靠模型自评产生质量结论。
